# Dispatcher Decision Rules

This is the inventory of the rules that decide the dispatcher's next step for an issue or PR (issue #555, Epic #519). `src/headless_pr_workflow/dispatcher/rules.py` records the same rules as data, and `tests/test_dispatcher_rules_registry.py` fails when the two name different rules, when a listed marker is no longer in its file, or when a row and the registry disagree on a marker or on a suspected disagreement.

The duplicate-rule guard (#570) reads the registry; the parity baseline (#571) proves or disproves each suspected disagreement; #556, #557 and Feature #526 move each rule into its owner. This inventory changes no decision. `src/headless_pr_workflow/next_action.py` is advisory and the dispatcher does not call it, so it is not listed. The board status display (`dispatcher/status.py`) appears only where it reads the same facts as a rule.

## Decision rules

How to read a row:

- **Implementations** names each file that implements the rule and, after the colon, the marker for each implementation: a function, variable, constant or jq name that appears literally in that file. The owner is the file the rule is meant to live in; every other file in the row is a known duplicate location, the allowlist that the guard (#570) shrinks.
- **Entry points**: `poll` is `scripts/dispatcher-poll.sh`; `invoke` is the new-work path of `scripts/dispatcher-invoke.sh` (Steps 1 to 6, the `/implement` hand-off and `next_new_work`); `resume` is `run_resume_pass` and its steps; `codex-worker` is `scripts/codex-worker.sh`, which runs `codex_worker.py`.
- **Tests** are the files under `tests/` that exercise the rule.
- **Copies** is `Single copy` when only one file implements the rule, `Agree` when the copies are believed to match, and **Suspected:** with the reason when they are suspected to disagree.

## How the duplicate-rule guard recognises a rule

`src/headless_pr_workflow/dispatcher/rule_guard.py` (tests: `tests/test_dispatcher_rule_guard.py`, issue #570) reads the registry. For each marker of a rule it looks in every file under `scripts/` and `src/` for a definition of that name: `def <marker>`, a shell function definition (`<marker>() {`, or `<marker>()` with the brace on the next line, or `function <marker>`), or an assignment `<marker>=` or `<marker> =`. It fails when:

- a file the registry does not list for the rule defines one of its markers (a new copy outside the owner that is not on the allowlist), or
- an allowlisted duplicate no longer contains its marker (the copy is gone, so the registry entry must be removed and the allowlist shrinks).

Limits of the match: it is by name, so a renamed copy, an inline copy with no named definition (for example a jq filter written in a pipeline) and a call to a marker (including a zero-argument Python call such as `<marker>()`) are not found; a generic marker can match an unrelated definition, so a rule needs a distinctive marker (`decide` was dropped from `codex_eligibility_reserve` for this reason); tests and docs are not scanned. When a consolidation story removes a copy, it removes the entry from `rules.py` and the inventory row in the same PR.

## Parity baseline

`tests/test_dispatcher_parity_in_flight.py` (issue #571) records, for the in-flight PR-fact rules below, what each copy decides for the same GitHub facts: open and closed PRs, the story and its comments, and the merge-gate line. Shell copies run in bash against a fake `gh` that returns only the first 100 items of a list read without `--paginate`; Python copies get a fake gateway whose failing reads raise. The cases include unreadable facts, a failed comment (marker) read, unknown mergeability and more than 100 open PRs. The test fails when a copy's decision changes, or when a case is listed below and its copies agree, or the other way round. The new-work admission rules and the Codex and usage rules (#583) have their own files, below.

Fixtures per rule: `linked_pr_lookup`, `merged_pr_finish`, `merge_gates_pass`, `in_flight_step`, `draft_ready_signal`, `open_blocker`, `po_unblock`: each is a key of `CASES` in `tests/test_dispatcher_parity_in_flight.py`.

Resolution classes follow Feature #525 → Decisions → Divergent copies of one rule: **contract** keeps the behavior a documented contract requires; **read defect** follows the complete, fail-closed read; **PO decision** needs the PO's answer, and the rule stays on the guard allowlist until then. The consolidating story (#556, #557) declares that `Type: decision` blocker.
